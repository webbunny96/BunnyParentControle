## Загальна архітектура

Система складається з трьох основних компонентів:

```
┌─────────────────────────────────────────────────────────┐
│                    Parent Control System                 │
├─────────────────────────────────────────────────────────┤
│                                                          │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────┐  │
│  │   Monitor    │    │ Telegram Bot │    │   GUI    │  │
│  │   Service    │◄───┤              │◄───┤  App     │  │
│  │              │    │              │    │          │  │
│  └──────┬───────┘    └──────┬───────┘    └────┬─────┘  │
│         │                    │                  │        │
│         └────────────────────┼──────────────────┘        │
│                              │                           │
│                    ┌─────────▼─────────┐                 │
│                    │   config.json    │                 │
│                    └──────────────────┘                 │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### Компоненти

1. **Monitor Service** (`main.py`) - Головний сервіс моніторингу
2. **Telegram Bot** (`src/bot/`) - Віддалене управління через Telegram
3. **GUI App** (`src/gui/`) - Локальний інтерфейс користувача

## Компоненти системи

### 1. Monitor Service (main.py)

**Призначення:** Головний сервіс, який постійно моніторить стан системи та визначає потребу в блокуванні.

**Відповідальність:**
- Завантаження конфігурації
- Запуск GUI додатку як окремого процесу (за замовчуванням)
- Перевірка умов блокування (кожні 10 секунд)
- Запуск вікна блокування при потребі
- Запуск Telegram бота як окремого процесу
- Моніторинг стану GUI процесу та автоматичне завершення при закритті GUI
- Обробка callback функцій блокування/розблокування

**Архітектура:**

```
main.py
├── Завантаження конфігурації
├── Запуск GUI додатку (subprocess, опціонально)
├── Запуск Telegram бота (subprocess)
├── Моніторинг GUI процесу (async task)
├── monitor_logic()
│   ├── Цикл перевірки (кожні 10 секунд)
│   ├── should_block() - перевірка умов
│   ├── on_block_callback() - запуск вікна блокування
│   └── on_unblock_callback() - закриття вікна блокування
└── Обробка помилок та завершення
```

**Потоки виконання:**
- Головний потік: моніторинг та обробка callback
- Процес GUI: окремий процес для GUI додатку (system tray)
- Процес бота: окремий процес для Telegram бота
- Процес вікна блокування: окремий процес для вікна блокування
- Async task: моніторинг стану GUI процесу

**Особливості:**
- При закритті GUI додатку автоматично завершується весь сервіс
- Можливість запуску без GUI через опцію `--no-gui`
- Коректне завершення всіх процесів при зупинці

### 2. Telegram Bot (src/bot/)

**Призначення:** Віддалене управління системою через Telegram.

**Відповідальність:**
- Обробка команд від користувачів
- Реєстрація адміністраторів
- Управління конфігурацією через callback
- Відображення статусу системи

**Архітектура:**

```
src/bot/
├── main.py          # Точка входу, ініціалізація бота
├── handlers.py      # Обробники команд та callback
└── keyboards.py     # Клавіатури для інтерфейсу
```

**Обробка подій:**

```
Повідомлення/Command
    │
    ├── /start → cmd_start_handler()
    │   ├── Перевірка deep link (QR-код)
    │   ├── Реєстрація адміністратора
    │   └── Показ головного меню
    │
    ├── /status → cmd_status_handler()
    │   └── Відображення статусу
    │
    └── Callback → process_callbacks_handler()
        ├── block/unblock → зміна force_block
        ├── schedule_menu → налаштування розкладу
        ├── time_* → встановлення ліміту часу
        └── change_password → зміна пароля
```

**Стан конфігурації:**

Бот читає та записує конфігурацію через `src/core/config.py`:
- Читання: перед кожною операцією
- Запис: після зміни налаштувань
- Синхронізація: через файл `config.json`

### 3. GUI App (src/gui/)

**Призначення:** Локальний інтерфейс користувача з system tray.

**Відповідальність:**
- Показ system tray іконки
- Вікно налаштувань (токен бота, пароль)
- Генерація QR-коду для реєстрації
- Захист паролем для доступу до налаштувань

**Архітектура:**

```
src/gui/
├── main.py              # Точка входу
├── tray_app.py          # System tray додаток
├── settings_window.py    # Вікно налаштувань
├── password_dialog.py    # Діалог пароля
└── blocking_window.py    # Вікно блокування
```

**Життєвий цикл:**

```
Запуск GUI
    │
    ├── Перший запуск?
    │   ├── Так → Показ налаштувань (обов'язково)
    │   │   └── Очікування встановлення пароля
    │   │
    │   └── Ні → Запуск system tray
    │
    ├── System Tray
    │   ├── Клік "Налаштування" → PasswordDialog → SettingsWindow
    │   └── Клік "Вихід" → PasswordDialog → Закриття
    │
    └── Головний цикл (mainloop)
```

**Потоки:**

- Головний потік (GUI): обробка подій Tkinter
- Tray потік: обробка подій system tray (через `threading`)

### 4. Core Modules (src/core/)

**Призначення:** Ядро системи з логікою бізнес-процесів.

#### config.py

**Відповідальність:**
- Завантаження/збереження конфігурації
- Нормалізація конфігурації (додавання відсутніх полів)
- Валідація конфігурації
- Міграція зі старих форматів

**Особливості:**
- Атомарне збереження (спочатку в тимчасовий файл)
- Автоматична нормалізація при завантаженні
- Підтримка міграції `admin_id` → `admin_ids`

#### monitor.py

**Відповідальність:**
- Визначення потреби в блокуванні
- Моніторинг стану системи
- Обробка callback функцій

**Логіка блокування:**

```
should_block(config)
    │
    ├── force_block == True? → Так → БЛОКУВАННЯ
    │
    ├── time_limit > 0?
    │   ├── Так → Час вичерпано? → Так → БЛОКУВАННЯ
    │   └── Ні → Продовжити
    │
    └── Розклад активний? → Так → БЛОКУВАННЯ
        └── Ні → РОЗБЛОКОВАНО
```

**Пріоритети:**
1. Force block (найвищий)
2. Ліміт часу
3. Розклад

#### scheduler.py

**Відповідальність:**
- Перевірка чи поточний час в розкладі
- Валідація розкладу
- Обробка нічних інтервалів (наприклад, 22:00 - 07:00)

**Обробка нічних інтервалів:**

```
start_time > end_time (наприклад, 22:00 - 07:00)
    │
    ├── Поточний час >= start_time? → Так → БЛОКУВАННЯ
    │
    └── Поточний час <= end_time? → Так → БЛОКУВАННЯ
```

### 5. Utils (src/utils/)

**Призначення:** Допоміжні модулі для роботи системи.

#### logger.py

Централізоване логування з підтримкою файлів та консолі.

#### qr_generator.py

Генерація QR-кодів для реєстрації адміністраторів.

#### telegram_api.py

Робота з Telegram Bot API (отримання username, валідація токену).

#### env_manager.py

Управління `.env` файлом (читання/запис токену).

## Потоки даних

### Зміна конфігурації

```
Користувач (Telegram/GUI)
    │
    ├── Зміна налаштувань
    │   │
    │   └── save_config() → config.json
    │
    └── Monitor Service
        │
        ├── load_config() → Читає config.json
        │
        └── Перевірка умов блокування
```

### Блокування комп'ютера

```
Monitor Service
    │
    ├── should_block() → True
    │
    ├── on_block_callback()
    │   │
    │   └── Запуск blocking_window.py (subprocess)
    │       │
    │       ├── Блокування вводу (BlockInput)
    │       ├── Повноекранне вікно
    │       └── Відлік до вимкнення
    │
    └── Користувач розблокує через бота
        │
        ├── force_block = False → config.json
        │
        └── Monitor Service виявляє зміну
            │
            └── Закриття вікна блокування
```

### Реєстрація адміністратора

```
GUI App (Settings Window)
    │
    ├── Генерація QR-коду
    │   │
    │   ├── create_auth_url(bot_username, otp)
    │   │
    │   └── generate_qr_code(url)
    │
    └── Користувач сканує QR-код
        │
        ├── Telegram → /start?otp=ABCD1234
        │
        ├── cmd_start_handler()
        │   │
        │   ├── Перевірка OTP
        │   │
        │   └── Додавання user_id до admin_ids
        │       │
        │       └── save_config() → config.json
```

## Взаємодія компонентів

### Monitor Service ↔ Bot

**Зв'язок:** Через файл `config.json`

```
Monitor Service          Bot
    │                     │
    │  Читає config.json  │
    │◄────────────────────┤
    │                     │
    │  Змінює config.json │
    │────────────────────►│
    │                     │
    └─────────────────────┘
```

**Синхронізація:**
- Monitor Service читає конфігурацію кожні 10 секунд
- Bot читає конфігурацію перед кожною операцією
- Обидва компоненти записують конфігурацію після змін

### Monitor Service ↔ Blocking Window

**Зв'язок:** Через subprocess та моніторинг конфігурації

```
Monitor Service
    │
    ├── Запуск blocking_window.py (subprocess)
    │
    ├── Моніторинг процесу
    │
    └── Перевірка конфігурації
        │
        ├── force_block == False?
        │   │
        │   └── Так → Закриття процесу
        │
        └── Ні → Продовження моніторингу
```

### GUI ↔ Bot

**Зв'язок:** Через конфігурацію та QR-код

```
GUI App
    │
    ├── Генерація QR-коду (з OTP з config.json)
    │
    └── Користувач сканує → Bot реєструє адміністратора
```

## Архітектурні рішення

### 1. Файлова конфігурація

**Рішення:** Використання JSON файлу для конфігурації.

**Переваги:**
- Простота реалізації
- Легко читати/редагувати вручну
- Не потребує бази даних

**Недоліки:**
- Потенційні проблеми з конкурентним доступом
- Немає транзакцій

**Мітигація:**
- Атомарне збереження (тимчасовий файл)
- Короткі інтервали між операціями

### 2. Subprocess для бота та вікна блокування

**Рішення:** Запуск бота та вікна блокування як окремих процесів.

**Переваги:**
- Ізоляція помилок (збій одного компонента не впливає на інші)
- Незалежне завершення процесів
- Простіше налагодження

**Недоліки:**
- Більше споживання ресурсів
- Складніша комунікація між процесами

### 3. Асинхронний Telegram бот

**Рішення:** Використання aiogram 3.x з async/await.

**Переваги:**
- Ефективна обробка запитів
- Підтримка великої кількості користувачів
- Сучасний підхід до розробки

### 4. System Tray для GUI

**Рішення:** Використання pystray для system tray та Tkinter для вікон.

**Переваги:**
- Мінімальне споживання ресурсів
- Зручний доступ до налаштувань
- Нативний вигляд

**Недоліки:**
- Залежність від платформи (Windows)
- Складність синхронізації потоків

### 5. Блокування вводу через Windows API

**Рішення:** Використання `BlockInput()` з Windows API.

**Переваги:**
- Ефективне блокування миші та клавіатури
- Неможливо обійти без прав адміністратора

**Недоліки:**
- Працює тільки на Windows
- Потребує прав адміністратора

### 6. Захист паролем

**Рішення:** Зберігання пароля у відкритому вигляді в `config.json`.

**Переваги:**
- Простота реалізації
- Швидкий доступ

**Недоліки:**
- Небезпека (пароль у відкритому вигляді)
- Можливість втрати при збої

**Майбутні покращення:**
- Шифрування пароля
- Використання хешів замість відкритого пароля

## Масштабованість

### Поточні обмеження

1. **Один комп'ютер:** Система призначена для одного комп'ютера
2. **Файлова конфігурація:** Не підходить для багатокористувацьких систем
3. **Windows only:** Працює тільки на Windows

### Можливі покращення

1. **База даних:** Заміна JSON на SQLite або PostgreSQL
2. **Клієнт-сервер:** Розділення на сервер та клієнти
3. **Кросплатформенність:** Підтримка Linux та macOS
4. **Веб-інтерфейс:** Додавання веб-панелі управління

## Безпека

### Поточні заходи

1. **Пароль доступу:** Захист налаштувань паролем
2. **Реєстрація адміністраторів:** Тільки через QR-код або код
3. **Блокування вводу:** Неможливо обійти без прав адміністратора

### Потенційні загрози

1. **Відкритий пароль:** Пароль у `config.json` не зашифрований
2. **Файлова конфігурація:** Можливість редагування вручну
3. **Відсутність автентифікації:** Немає перевірки цілісності конфігурації

### Рекомендації

1. Шифрування конфігурації
2. Підпис конфігурації для перевірки цілісності
3. Логування всіх змін конфігурації
4. Резервне копіювання конфігурації
